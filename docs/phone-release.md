# Releasing the phone app

The phone's JavaScript ships over the air with `expo-updates` and EAS Update, and a store build happens only when its native fingerprint has none ([ADR 0032](adr/0032-the-phone-ships-over-the-air-and-the-api-keeps-every-supported-release-working.md)). iOS goes to TestFlight and the App Store, Android to Google Play. Four GitHub workflows run both, and each skips with a notice until the setup below is done, so CI stays green without an Expo account.

## How a change reaches phones

Each platform's runtime version is its own native fingerprint (`runtimeVersion.policy: fingerprint` in `apps/mobile/app.json`), so an update is only offered to binaries of that platform with the same native code. `node scripts/phone-release.mjs runtime ios` or `runtime android` prints it. The two fingerprints always differ, and `eas update:republish` carries one runtime per update group, so every publish, republish and rollback runs once per platform and each platform has its own update groups. `app.json` lists its `platforms` because Expo otherwise detects web from whether `react-dom` is hoisted, which makes the fingerprint differ between a pnpm script and a plain `node` call. `apps/mobile/fingerprint.config.js` leaves `version` out of the fingerprint, so an update can carry a new release version without a new binary. `eas.json` and every key in `app.json`, Android ones included, are part of both fingerprints, so a change to either needs a new binary on both platforms.

An installed app checks for an update on every launch without waiting for it, so an update downloads on one launch and runs from the next. Until an update arrives, or when one cannot load, the app runs the bundle inside the binary. The `x-lymi-client` header names the running update, which the Worker adds to the phone's server outcomes as `app_update`.

The repository variable `PHONE_PLATFORMS` names the platforms the workflows release: `ios` when it is unset, `ios,android` once Google Play is set up.

| Workflow | When | What it does |
| --- | --- | --- |
| Phone beta | Each green CI run on `main`, or by hand | For each platform, when the phone or a shared package changed since its last beta update, publishes an update to the `beta` branch. A run by hand also starts a `beta` build when no build has this runtime yet; an automatic run leaves a warning instead, and beta installs keep their last update until someone runs it. The iOS build goes to TestFlight; the Android build goes to Play's internal testing track. The iOS build carries no What to Test notes, which EAS Submit accepts only on the Enterprise plan. |
| Phone promote | By hand, once a week | Stops unless every platform's latest beta update comes from the same commit. Runs the Phone smoke journey on that commit and freezes its API contract, and stops if either fails or the contract is not on `main` yet. Then checks, for every platform, that beta still has that update and no production rollout is running, and only then republishes each to `production` for 10% of installs. For each runtime with no `production` build it starts one: iOS uploads to App Store Connect, Android to Play's closed testing track. |
| Phone rollout | Every six hours, or by hand | On each platform, widens a `production` rollout that is at least a day old to every install. |
| Phone rollback | By hand | Reverts the newest update on `production` or `beta`, on both platforms or one: a partial rollout is reverted, otherwise the previous update on the same runtime is republished, or the binary's own bundle when there is none. A group ID input republishes that update instead, on its own platform. |

The first run of any of them creates the `beta` and `production` channels and their branches when the project lacks them; both platforms share them. Promote, rollout and production rollback share one `phone-production` lock, so they never change production at the same time. The smoke journey runs in the iOS Simulator only; Android ships the same JavaScript from the same commit. Its build turns updates off, so it always tests the bundle it embedded.

Each release version keeps its frozen contract in `apps/mobile/contract/<version>.json` until the minimum version passes it. Both platforms share `expo.version`, so one contract covers both. Promote fails before publishing when the commit calls an API that differs from the contract already frozen for its version; raise `expo.version` in `app.json`, merge it, let Phone beta publish it, then promote. A version with no contract on `main` publishes nothing: Promote opens a pull request with its contract; merge it once CI has checked the Worker against it, and the next Promote goes ahead.

Every EAS call goes through `scripts/phone-release.mjs`. `node scripts/phone-release.mjs manifest` installs the pinned `eas-cli`, runs a sample of every call for both platforms through that CLI's own parser, values included, and records its command list and the accepted calls in `scripts/eas-cli-commands.json`. The tests fail when a call differs from what the parser accepted, so run it after changing a call or the pin.

`beta` builds read the `beta` channel and `production` builds the `production` channel, with one bundle identifier and package, `app.lymi` ([`apps/mobile/eas.json`](../apps/mobile/eas.json)). Android builds are app bundles (`.aab`), which Play requires. EAS owns the iOS build number and the Android version code (`appVersionSource: remote`), each counted on its own. The free plan has 15 iOS and 15 Android builds a month, counted from the first of the month in UTC, and a native change costs up to two of each: one for beta, started by hand, and one at Promote. Several native changes can share one beta build when Phone beta runs by hand after the last of them. Failed builds count too; `npx eas-cli@24.13.0 account:usage krambertech` shows what is left. Submitting an iOS version for review in App Store Connect, and promoting an Android release from closed testing to production in Play Console, stay a person's steps.

Each update's Hermes source maps go to PostHog's error tracking from Phone beta, once per platform, and Promote republishes the same files. Metro writes a chunk ID into every bundle (`getPostHogExpoConfig` in `apps/mobile/metro.config.js`), which is how PostHog finds the map for a frame. On EAS release builds, `with-source-maps.cjs` uploads the embedded bundle's map with PostHog's own tooling: on iOS it wraps the app's bundle phase, which preserves the Metro map, clones its chunk ID into the composed Hermes map and uploads it after bundling; on Android it applies PostHog's `posthog.gradle`, which does the same after the release bundle task. A missing key or failed upload fails the build on both. The EAS pre-install hook installs the pinned CLI. Local and debug builds bundle without uploading; the gate runs at build time so the native fingerprint stays the same on every machine. [PostHog's React Native guide](https://posthog.com/docs/error-tracking/upload-source-maps/react-native) describes both upload paths.

Both upload paths use PostHog's `event` release mode: maps are matched by chunk ID, while an exception's `$app_namespace`, `$app_version` and `$app_build` name its release. Republishing an OTA or building another binary does not bind its shared maps to the first binary's build number; `app_update` names the bundle that actually ran.

## Setting it up

Do these once, in order. Steps 1 to 3 change `app.json` or `eas.json`, which are part of the fingerprint, so finish them before the first build. The bundle identifier and the Android package are both `app.lymi`; neither can change after the first upload.

1. **Create a free Expo account** at expo.dev. Then, in `apps/mobile`, run `npx eas-cli@24.13.0 login` and `npx eas-cli@24.13.0 init --force --non-interactive` to create the project. `init` rewrites `app.json` with the config the plugins resolve, so restore the file and add only `owner`, `extra.eas.projectId`, and `updates.url` as `https://u.expo.dev/<projectId>`, which is what `update:configure` would add. Commit `app.json`.
2. **Enrol in the Apple Developer Program** (#507) and create the app in App Store Connect with the bundle identifier `app.lymi`.
3. **Give EAS the Apple credentials.** Run `npx eas-cli@24.13.0 credentials --platform ios` in `apps/mobile` and sign in to Apple when asked. Let it create the distribution certificate and the provisioning profiles for the app and its widget extension, and add an App Store Connect API key for EAS Submit. Then add the app's numeric Apple ID as `ascAppId` to both `submit` profiles in `eas.json`, and the Apple Team ID as `ios.appleTeamId` in `app.json`, which `@bacons/apple-targets` needs to sign the extensions. Commit both.
4. **Add the repository secrets** under Settings, Secrets and variables, Actions:
   - `EXPO_TOKEN`: an access token from expo.dev, Account settings, Access tokens. A robot user with the Developer role on the project is safer than a personal token.
   - `POSTHOG_CLI_API_KEY`: a PostHog personal API key scoped to project 292417 with `error tracking write` and `organization read`. Without it, OTA updates still ship and the workflow warns that their errors stay unreadable; acceptance requires a successful upload, not a green workflow.
   - `RELEASE_GITHUB_TOKEN`: a fine-grained token for this repository with read and write access to contents and pull requests, so Promote's contract pull request runs CI. Without the token, Promote stops on a new version and attaches its frozen contract to the run for a person to commit.
5. **Run Phone beta by hand** from the Actions tab. It publishes the first beta update and starts the first build, which reaches TestFlight once Apple has processed it.

Add the same `POSTHOG_CLI_API_KEY` as a secret in both EAS environments, `preview` for beta and `production` for the stores. GitHub repository secrets do not reach the remote EAS builder. `eas.json` supplies the EU host and project ID, and the app reaches `https://my.lymi.app` by default. Never use an `EXPO_PUBLIC_` name for the upload key or put it in `app.json`.

## Setting up Google Play

Android ships once these steps are done. Until `PHONE_PLATFORMS` names `android`, the workflows build and publish nothing for it, so no Android build counts against the quota.

1. **Create a Google Play developer account** at play.google.com/console, as a personal account, and pay the one-time fee. Google verifies your identity and, for a personal account, a phone number and an Android device in your name; this can take a few days.
2. **Create the app.** In Play Console, choose Create app, name it Lymi, pick English (United States) as the default language, App, and Free. Accept the declarations.
3. **Create the service account for EAS Submit.** In Google Cloud Console, create or pick a project, enable the Google Play Android Developer API, then go to IAM & Admin, Service accounts, Create service account. Name it `eas-submit` and skip the roles. Open it, choose Keys, Add key, Create new key, JSON, and keep the downloaded file outside Git.
4. **Let the service account release.** In Play Console, go to Users and permissions, Invite new users, and enter the service account's email. Under App permissions add Lymi, and grant View app information, Edit and delete draft apps, Release to production, exclude devices, and use Play App Signing, Release apps to testing tracks, Manage testing tracks and edit tester lists, and Manage store presence. Invite the user.
5. **Give the key to EAS.** In `apps/mobile`, run `npx eas-cli@24.13.0 credentials --platform android`, choose the `production` profile, then Google Service Account, Upload a Google Service Account Key, and give it the JSON file. EAS keeps it per package and uses it for both profiles, so `eas.json` names no key file. Delete the downloaded file once EAS has it. In the same menu, let EAS generate the Android keystore if it has none; it becomes the upload key.
6. **Make the first upload by hand.** Google's API refuses a package that Play Console has never seen. Set the repository variable `PHONE_PLATFORMS` to `ios,android` under Settings, Secrets and variables, Actions, Variables, and run Phone beta by hand. The Android build succeeds and its submission fails with "Package not found". Download the `.aab` from the build's page on expo.dev. In Play Console, go to Test and release, Testing, Internal testing, Create new release, keep the Google-generated app signing key, upload the `.aab`, and roll it out. Add yourself to the internal testers list. Every later build submits by itself.
7. **Copy the signing fingerprints into the Worker.** See [Android App Links](#android-app-links).
8. **Fill in App content.** Under Policy and programs, App content, answer every declaration: privacy policy `https://lymi.app/privacy`; app access, with a test account Google's reviewers can sign in with; ads (none); the content rating questionnaire; target audience; data safety; government and financial features (none). In Data safety, say that the app lets people create an account, that they can delete it in the app (You, Delete account), and give `https://my.lymi.app/settings/delete-account` as the web link for deleting an account and its data.
9. **Run the closed test.** A personal account created after 13 November 2023 can apply for production only after a closed test that has had at least 12 testers opted in for the last 14 days in a row. A tester who leaves and rejoins starts their 14 days again. Go to Test and release, Testing, Closed testing, the Alpha track, and add a Google Group or an email list of at least 12 testers, more to allow for drop-outs. Share the opt-in link; each tester must accept it and install Lymi from Play. Phone promote's next `production` build lands on this track. Keep the testers opted in for the whole 14 days.
10. **Apply for production.** On the Dashboard, choose Apply for production and answer the three sections about the closed test, the app, and production readiness. Google answers within about a week.
11. **Promote to production.** Once access is granted, complete the store listing, then in Closed testing choose Promote release, Production, and send it for review. Later releases follow the same path: Phone promote uploads the binary to closed testing, and you promote it to production in Play Console.

The internal testing track takes up to 100 testers without review, like TestFlight. A closed testing release goes through Google's review before testers see it.

### What Play checks in the binary

- **Target API level.** New apps and updates must target Android 16 (API level 36) from 31 August 2026. React Native 0.86 already sets `targetSdk = 36` and `compileSdk = 36`, so `app.json` sets neither.
- **Permissions.** The merged manifest asks for the internet, network and Wi-Fi state, vibration, audio settings, notifications, boot completion, the camera, and storage up to Android 12 only. `android.blockedPermissions` removes `RECORD_AUDIO`, which `expo-image-picker` adds for video, and `SYSTEM_ALERT_WINDOW` from the template; Lymi records nothing and draws no overlays. No exact-alarm, location, media-library or foreground-service permission is requested, so Play asks for no permission declaration.
- **Notifications.** Android 13 and later ask before showing a notification. `askPermission()` in `apps/mobile/src/reminders/notifications.ts` asks when the learner turns the reminder on, which `POST_NOTIFICATIONS` from `expo-notifications` allows. The daily reminder is an inexact local notification, so it needs no `SCHEDULE_EXACT_ALARM`.
- **Icons.** The adaptive icon has foreground, background colour and monochrome layers, so Android 13 can theme it. The notification icon is one shape on a transparent background, because Android draws it in a single colour.

## Android App Links

Join and Add to Lymi links on `my.lymi.app` open the app once the Worker's `/.well-known/assetlinks.json` lists the certificates that signed it. Until `ANDROID_CERT_FINGERPRINTS` is set, the file answers 404 and the links open the website.

Play App Signing re-signs every install from Play with Google's app signing key, while EAS signs the upload with the upload key. List both, so the Play install and any build installed straight from EAS verify. Copy both SHA-256 fingerprints from Play Console, Test and release, App integrity, then Settings under Play app signing: the App signing key certificate and the Upload key certificate. `npx eas-cli@24.13.0 credentials --platform android` shows the upload key's SHA-256 too, which must match. Set them on the product Worker as one comma-separated value, colons kept:

```bash
pnpm --filter @lymi/web exec wrangler secret put ANDROID_CERT_FINGERPRINTS
```

Then open `https://my.lymi.app/.well-known/assetlinks.json` and check it lists both. Android checks the file when the app is installed or updated, so reinstall to see a link open the app. On a device, `adb shell pm get-app-links app.lymi` shows `verified` for `my.lymi.app`.

## Checking a release

`npx eas-cli@24.13.0 update:list --branch beta --platform ios` (or `--platform android`) lists each platform's updates with their runtimes, one runtime per fingerprint. A TestFlight or internal testing install picks up a beta update on its second launch after publishing. After a native change, `eas build:list --platform ios` and `--platform android` show a new build with a new runtime, and older binaries keep getting only updates for their own runtime.

For Error Tracking acceptance, test both bundles on a real TestFlight install under an account in `INTERNAL_ACCOUNT_IDS`, and the same on a Play internal testing install. The explicit link `lymi:///you?verify_phone_errors=source-maps` captures one handled exception per launch from `verifyReleaseException` in `apps/mobile/src/telemetry/posthog.ts` and flushes it; ordinary accounts, production-channel binaries and development/local builds cannot run it. The error message is scrubbed like every other exception, and the probe adds no usage event or private content.

1. Install a fresh beta binary, launch it without a network connection so no OTA can download, then restore connectivity without relaunching and open the link. Record the event in [Lymi Error Tracking](https://eu.posthog.com/project/292417/error-tracking), including an application frame's real source file and line, its chunk ID, `$app_version`, `$app_build` and `app_update`. An embedded bundle can have an Expo-generated update ID; a missing ID is recorded as null, never guessed from the newest published update.
2. Let the beta update download, relaunch to run it, and open the link again. Read back the new exception and confirm its `app_update` is the running OTA's ID, its frame resolves to the source file and line, and its version/build match that bundle and binary. The frame's chunk ID must match a symbol set with an uploaded file and no failure; a `last_used` timestamp alone does not prove resolution.
3. Open the same link in a development build against production and a release build against a local Worker; neither emits an exception. Keep the device/build/update identifiers, event links and resolved frame evidence with the release check. Unit tests of the gates and successful EAS jobs do not establish TestFlight or Play acceptance.

## Sign in with Apple

Enable Sign in with Apple on the `app.lymi` App ID as a primary App ID. Register the Services ID `app.lymi.web`, associate it with that primary App ID, and configure domain `my.lymi.app` with return URL `https://my.lymi.app/api/auth/callback/apple`. Apple requires HTTPS and does not accept localhost return URLs.

Register `notifications@lymi.app` as an email source in Sign in with Apple for Email Communication, with SPF or DKIM passing, so account emails reach learners who choose Hide My Email.

Create a Sign in with Apple key for that primary App ID and keep the downloaded `.p8` outside Git. Set the product Worker's `APPLE_APP_BUNDLE_IDENTIFIER=app.lymi`, `APPLE_CLIENT_ID=app.lymi.web`, `APPLE_TEAM_ID`, `APPLE_KEY_ID`, and `APPLE_PRIVATE_KEY` as encrypted secrets. The private key is the full PKCS #8 PEM. Keep these secrets out of previews, logs, and pull requests. The Worker signs its own short-lived client secrets, so no static JWT needs periodic replacement.

The native module and `ios.usesAppleSignIn` entitlement require a new signed binary; an over-the-air update cannot add them. Rebuild provisioning profiles with the capability, then verify a fresh sign-in, Hide My Email, cancellation, repeat sign-in after relaunch, and account deletion on a physical iPhone. The Simulator does not prove Apple account authentication or grant revocation. On the web, verify the HTTPS callback, the original return destination, and sign-in to the same account used by the phone.
